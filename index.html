02 exactly once

Two things that quietly go wrong in apps, and how I stop them.

You don't need to be an engineer for these. Press the buttons and read what happens. They're small simulations of how I handle these problems at TravLounge. They run in your browser and the timings are made up, but the steps are the real ones. Engineers can switch on the raw server log.

Pay once, get booked once

When you pay on TravLounge, the payment company (Razorpay) sends our server a short message saying the payment went through. Engineers call that message a webhook. If our server is slow to reply, Razorpay sends the same message again to be safe. A careless server treats the repeat as a new payment, and you end up with two bookings, two invoices and two WhatsApp messages.

Fast, but never out of date

The app's home screen shows banners, categories and your subscription. Fetching them from the database on every open would be slow, so the server keeps a ready-made copy in fast memory, called a cache. The risk is showing an old copy after something has changed. So each piece gets its own rule for when its copy is thrown away.

03 incident

The server that was full but looked idle, and how it got to 250 req/s.

A real problem from TravLounge production, written up the way I'd write it for my team. October 2026.

found by
a load test I ran against production
symptom

status
fixed
result
up to 250 requests a second

What we saw

Under load, each copy of the API server handled about 15 requests a second, no matter what we threw at it. Normally that's when AWS adds more servers. It didn't, because AWS was told to scale when CPU went above 70%, and CPU was sitting at 37%. The server was full, but it looked idle, so nothing came to help.

CPU while maxed out
scale-up at 70%
37%

Why

Each server copy ran 3 workers, and each worker served one request at a time. A request took about 200 ms, and most of that was spent waiting on the database, Elasticsearch or Redis rather than using the CPU. That makes 3 workers × 5 requests a second = 15 a second, with the CPU mostly waiting.

The fix

I let each worker take 4 requests at once using threads. While one request waits on the database, another runs. Python's GIL doesn't get in the way here, because it's released while waiting on the network. That gives 12 requests in flight per server copy instead of 3.

before3 at a time
after12 at a time

The details that would have bitten later

  • Dropped connections. Threaded workers keep connections open, so keep-alive is set to 75 s, longer than the load balancer's 60 s. If it were shorter, the server could close a connection the load balancer is about to reuse, and users would see random 502 errors.
  • Database connections. Every request in flight holds its own database connection, so one server copy can now use up to 12. I raised the database connection limit to 60 to match.
  • A quick undo. Changing how a live server runs is risky. If threads had caused problems, such as code that isn't safe to run in parallel or the database running out of connections, I didn't want to be writing a fix under pressure. So the thread count is a setting, and setting it back to 1 restores the old behaviour with a restart: no code change, no new build.

Same day: the slowest endpoint

The load test also showed the "active subscriptions" endpoint was slow. Three causes, three fixes:

  • It queued a cleanup job on every request. Now it runs at most once every 10 minutes.
  • It ran a separate database query for each item in the list (an N+1 query). Now it loads them in one batch.
  • It's now cached per user in Redis. The cache is cleared the moment a subscription is bought, used or cancelled, and if Redis is down the endpoint falls back to the database.

Then: the database itself

Threads let the server wait on the database more efficiently, but every request still waited. So I went after the wait itself:

  • done Moved the database to an Asian region, next to the app servers, so each query spends less time travelling over the network.
  • done Moved to a larger database instance that can serve the higher connection count.
  • done Worked through the slowest queries one by one.

Result

before~15 req/s
after250 req/s

The API now handles up to 250 requests a second, up from a ceiling of about 15. Autoscaling can see the load again, because a busy server now actually uses its CPU.

jobscarp

Sep 2026 · personal project · Python · FastAPI · Postgres · Gmail API · LLM

It reads job-alert emails from Cutshort and Instahyre through the official Gmail API, then parses, normalises and deduplicates them. Each job gets a score against my own profile and goes into a review queue that syncs to Google Sheets. It never scrapes, never logs in anywhere, and never applies on its own.

The decision: the LLM isn't allowed to score. The match score comes from a fixed weighted formula over parsed fields (skills 30%, experience 15%, salary 15%, and so on). The model only writes the narrative on top: fit, red flags, a draft message. Scoring stays testable and explainable, and it can't make up experience I don't have. 80+ tests.
